# Working notes for Claude Code

- LuaJIT (Lua 5.1 compatible, like WoW) is installed but not on PATH: `%LOCALAPPDATA%\Programs\LuaJIT\bin\luajit.exe`. After editing Lua, syntax-check each file with `luajit -bl <file>.lua` (exit code non-zero = error). This only checks syntax; the WoW API is not available, so nothing is actually run. Say so plainly.
- Run the checks from AGENTS.md "Checks" before reporting a change: `luajit tests/run.lua` (LuaJIT path above), StyLua (`%LOCALAPPDATA%\Microsoft\WinGet\Packages\JohnnyMorganz.StyLua_Microsoft.Winget.Source_8wekyb3d8bbwe\stylua.exe`), luacheck (`%USERPROFILE%\.luarocks\bin\luacheck.bat` with `LUA_PATH=<repo>/tools/?.lua;;`, because there is no C compiler for LuaFileSystem; `tools/lfs.lua` stands in), LuaLS (`lua-language-server --check=<repo> --checklevel=Warning`). Raise `tests/MIN_COVERAGE` when coverage grows.
- When formatting, compare the LuaJIT bytecode before and after (`luajit -bl`, with line numbers stripped): StyLua must not change behaviour.
- Lua patterns have no alternation: `(A|B)` does not work. Match a generic prefix, then compare in code.
- Match the surrounding style: tab indentation, `local addonName, ns = ...` header, `ns.T("KEY")` for every player-facing string (add the key to `Locale.lua`).
- Start every task with the docs, as AGENTS.md "Before you start any change" says: the matching `docs/ARCHITECTURE.md` section first, then the API docs of every Blizzard function / event you touch. Do this for bug hunts and reviews too: a suspected bug in a Blizzard call (argument or return order, nil, secret value) is confirmed in the API docs before it is reported or fixed, and the reply cites the doc file and line.
- **Look at the debug data before guessing.** The user plays with Behavior > Debug > "Collect debug data" on. The game writes it into the character's SavedVariables on `/reload` and logout: `C:\Program Files (x86)\World of Warcraft\_classic_beta_\WTF\Account\<account>\<realm>\<character>\SavedVariables\KnowYourRotation.lua` (`KnowYourRotationCharDB.debug`; the file with debug data is the big one, the others are a few hundred bytes: list them with `ls -la`). Print one with `luajit tools/read_debug.lua <file>`. It says what the real client answers (value / SECRET / nil / error, in combat or not) and why a step was or was not offered (`addon says | <spell>`). When a bug report or an open question is about API behaviour (secret values, cooldowns, range, totems, aura reads), read it first and cite it; say so when there is no data for the question. It is a sample from one session and one character, not proof for every class.
- `ref/wow-ui-source` is a git submodule (Gethe/wow-ui-source, `forever` branch): the Blizzard UI code and API docs for the Forever client (`Interface/AddOns/Blizzard_APIDocumentationGenerated`). Search it with Grep (e.g. `Name = "UnitCastingInfo"`), then read the `Arguments` / `Returns` block. Never copy `ref/` into the AddOns folder. Fresh clone: `git submodule update --init --depth 1`.
- Do not commit or bump the version unless asked. When asked: bump `VERSION.txt` and `KnowYourRotation.toc` together, then copy the repo into the AddOns folder named in AGENTS.md.
- Releases are built by GitHub Actions (`.github/workflows/release.yml`), never by hand: bump `VERSION.txt` and the TOC, commit and push, then push a tag `v<version>` (it must match both). The workflow checks the versions, zips only the addon files, attaches a SHA-256 and a build attestation, and marks versions with a `-` (e.g. `-beta.1`) as pre-release. `.github/workflows/check.yml` runs a LuaJIT syntax check, a TOC / file list check, a version match check and luacheck on every push.
